## What this page is

CDF Page 2 lists every closing cost line item, grouped into lettered sections, each with
a computed subtotal, rolling up to one grand total (J). Sections:

- **A** — Origination Charges
- **B** — Services Borrower Did Not Shop For
- **C** — Services Borrower Did Shop For
- **D** — Total Loan Costs (Borrower-Paid) — *computed*, A + B + C
- **E** — Taxes and Other Government Fees
- **F** — Prepaids
- **G** — Initial Escrow Payment at Closing
- **H** — Other
- **I** — Total Other Costs — *computed*, E + F + G + H
- **J** — Total Closing Costs — *computed*, D + I

Every itemized row (A, B, C, E, F, G, H) shares one column shape, matching the SoftPro
grid exactly: Description, To (payee), Borrower-Paid At Closing, Borrower-Paid Before
Closing, Seller-Paid At Closing, Seller-Paid Before Closing, Paid By Others. SoftPro
exposes all five money columns on every section (not just the sections where a printed
CD shows a seller side) so staff can enter whichever applies — this build follows that,
consistent with the "everything stays editable, don't enforce business rules the shell
doesn't need to" pattern from every prior screen.

## Scope: manual entry + auto-summed totals (no cross-screen pull yet)

Additional Title Charges, Tax Prorations, Premiums, and Endorsements already carry
`cdf_line`/`bill_code` free-text fields — forward-compatible groundwork for eventually
routing those rows onto CDF/HUD automatically. That auto-aggregation is **not** built in
this pass: `cdf_line` is free text today (not a constrained section reference), and
Premiums/Endorsements don't even have a `cdf_line` column yet (only `bill_code`).
Wiring that up correctly — matching sections, handling splits, avoiding double-entry —
is a real feature on its own and isn't part of what Cam asked to start today. CDF Page 2
launches as its own manual-entry list, same shape as every other Escrow/Closing screen
so far. (Flagging this gap in the Parking Lot as a documented future increment, not
silently dropping it.)

Section subtotals (D, I) and the grand total (J) **do** auto-calculate — this is the
same "plain arithmetic on the user's own entered numbers" carve-out already established
for Tax Prorations' day-count math, not rate-table/proprietary data. Sums recompute from
live row data on every render (server-computed on page load, not a stored/silently-drifting
column), so unlike the "everything stays editable" one-time-fill fields (Calculate
buttons, Generate buttons), these are always-correct read-only display values, not
editable inputs — there's nothing to hand-correct in a running sum.

## Schema

One flat table, `cdf_page2_lines`, distinguished by a `section` column — same "flatten
templated sections into one table" pattern as Tax Prorations:

- id, order_id (fk orders, cascade), section text (`'A'|'B'|'C'|'E'|'F'|'G'|'H'`),
  sort_order
- description text
- to_contact_id uuid (fk contacts, set null) — the "To" column
- borrower_paid_at_closing numeric, borrower_paid_before_closing numeric
- seller_paid_at_closing numeric, seller_paid_before_closing numeric
- paid_by_others numeric
- created_at

RLS: standard blanket `authenticated` policy, matching every other title/escrow table.

D/I/J are never stored — computed in the server action from the live rows each time the
page loads.

## Types / constants

`CdfPage2Line` type. `CDF_PAGE2_SECTIONS` constant: ordered list of
`{ code, label }` pairs (A/Origination Charges ... H/Other) drives both the section
grouping in the UI and the fixed iteration order for computing subtotals.

## Server actions

`src/app/actions/cdf-page2.ts`:
- `listCdfPage2Lines(orderId)` — all rows, ordered by section (fixed order) then
  sort_order
- `computeCdfPage2Totals(lines)` — pure function, not a DB call: returns per-section
  subtotals plus D/I/J, each as `{ borrowerAtClosing, borrowerBeforeClosing,
  sellerAtClosing, sellerBeforeClosing }` (D omits seller since Loan Costs subtotals
  don't carry a seller column on the real form, even though the line-item grid does)
- `addCdfPage2Line(orderId, section)` — inserts into a specific section, sort_order =
  count of existing rows in that section + 1
- `updateCdfPage2Line(orderId, id, formData)`
- `deleteCdfPage2Line(orderId, id)`
- `listAllContacts(orderId)` — same pattern as Additional Charges

## Components / route

`src/components/title/CdfPage2Panel.tsx` — one section block per letter (A, B, C, D-subtotal,
E, F, G, H, I-subtotal, J-total), each itemized section rendering its rows the same way
Additional Charges does (`ChargeRow`-equivalent: own `<form>`, own `formRef`, own
`useAutosave` + `SaveIndicator`, "+ Add Item" per section, "Remove item" per row —
reload only on add/delete). Subtotal/total rows are plain computed display, not forms.

`src/app/orders/[id]/cdf-page-2/page.tsx` — standard auth-check + `Promise.all` fetch
(lines + contacts) + render.
